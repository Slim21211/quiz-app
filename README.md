# Quizroom

Каталог тематических квизов с Telegram Mini App, редактором вопросов и отдельной таблицей результатов для каждой игры. React 18, TypeScript, Redux Toolkit Query, SCSS Modules, Vite, Supabase/PostgreSQL и Telegraf. Фронтенд и две серверные функции размещаются одним проектом на Vercel.

## Возможности

- Создание квиза с названием и собственным адресом. Новый квиз сохраняется как черновик; после добавления вопросов его можно опубликовать или скрыть.
- Добавление, редактирование и удаление вопросов. С началом первой попытки состав вопросов фиксируется, чтобы участники играли на равных условиях. Для следующего набора вопросов создайте новый квиз.
- Одна попытка на Telegram-пользователя в каждом квизе. Продолжение начатой попытки открывает первый неотвеченный вопрос без повторного ввода имени; его исходный срок сохраняется. Сервер проверяет подпись `initData`, а не доверяет идентификатору из браузера.
- 60 секунд на вопрос. Ответ вводится одной строкой и отправляется кнопкой или Enter; переносы строк отклоняются сервером. Перезагрузка сохраняет исходный срок; поздний ответ считается пропуском. Повтор запроса не меняет уже сохранённый ответ. При возвращении просроченный текущий вопрос закрывается и начинается следующий.
- Ручная проверка с возможностью изменить или снять оценку. Подсказки отмечают совпадения после нормализации и перестановку одинаковых слов, но не выставляют баллы автоматически.
- Рейтинг каждого квиза включает только завершённые попытки с полностью проверенными ответами. Равные баллы дают одинаковое место. Незавершённые попытки и ожидающие проверки вынесены в отдельные блоки без баллов и мест; на мобильном результаты представлены карточками.
- Карточки каталога показывают личный статус и итоговый балл после проверки. Завершённый квиз нельзя запустить заново; начатую попытку можно продолжить. Статус загружается с сервера по проверенной Telegram-сессии или гостевой cookie, а просмотр каталога не регистрирует участника.
- Прокрутка к началу страницы при переходах между маршрутами, включая возврат назад. Закреплённая шапка, навигация одинаковой ширины, три видимых шага игры и выбор квиза с поиском и управлением с клавиатуры. Экран ввода имени можно закрыть кнопкой отмены без старта попытки.
- Адаптивный интерфейс без снега и эмодзи. Стили компонентов находятся в `src/App.module.scss`; `src/index.css` содержит общие токены, базовую типографику и сброс браузерных стилей.

## Локальный запуск

Нужен Node.js 22.12 или новее. Lock-файл включён в проект.

```sh
npm ci
npm run dev
```

Локальный адрес — `http://localhost:5173`. Команда запускает Vite вместе с `/api/quiz` и `/api/bot`. Обычный `vite` не подключает API, а `npm run preview` показывает только собранный фронтенд.

Для сервера задайте переменные окружения через среду запуска или локальный `.env`. Реальные значения в репозиторий добавлять нельзя. Существующие файлы с credentials при доработке не изменялись.

| Переменная | Назначение |
| --- | --- |
| `SUPABASE_URL` | URL проекта Supabase; без префикса `VITE_` |
| `SUPABASE_SERVICE_ROLE_KEY` | Серверный ключ Supabase, никогда не передавать в клиент |
| `SESSION_SECRET` | Независимый случайный секрет длиной минимум 32 символа для подписания сессий |
| `ADMIN_PASSWORD` | Сильный пароль администратора, минимум 16 символов, максимум 256; без пробелов по краям |
| `WEB_APP_URL` | Полный адрес приложения, например `https://quiz.example.com`; локально по умолчанию `http://localhost:5173` |
| `BOT_TOKEN` | Токен Telegram-бота; нужен для webhook и проверки Telegram `initData` |
| `TELEGRAM_WEBHOOK_SECRET` | Случайный секрет webhook, совпадающий с `secret_token` при регистрации в Telegram |
| `ALLOW_GUEST_PLAY` | Необязательно: `true` разрешает игру из обычного браузера. По умолчанию отключено |

`VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` больше не используются. Убедитесь, что серверный ключ и другие секреты не имеют префикса `VITE_`: Vite делает такие переменные доступными браузеру.

Для генерации `SESSION_SECRET`, `ADMIN_PASSWORD` и `TELEGRAM_WEBHOOK_SECRET` выполните локально:

```sh
npm run --silent secrets:generate
```

Скрипт использует `node:crypto`: каждое значение независимо создаётся из 32 случайных байтов и кодируется в base64url. Вывод имеет формат `ИМЯ=значение` для переноса в переменные окружения Vercel. Файлы не создаются и существующее окружение не меняется. Запускайте в своём терминале, не в CI с общедоступными логами. Каждый запуск создаёт новый набор; меняйте рабочие значения только при намеренной ротации. При замене `TELEGRAM_WEBHOOK_SECRET` нужно обновить `secret_token` зарегистрированного webhook. `BOT_TOKEN` выдаёт BotFather, а `SUPABASE_SERVICE_ROLE_KEY` берётся из проекта Supabase — этот скрипт их не создаёт.

В гостевом режиме попытка привязана к подписанной HttpOnly cookie. Очистка cookies или другой браузер позволяют начать заново. Для соревнований используйте вход через Telegram.

## База данных и обновление существующего проекта

Файл `supabase-schema.sql` предназначен и для новой базы, и для обновления прежней схемы. Самостоятельно к рабочей базе он не применяется. Перед применением нужны резервная копия, проверка на копии базы и явное согласование изменения схемы и доступа.

SQL выполняется одной транзакцией и:

1. Создаёт отсутствующие таблицы, включая `shown_questions` и `request_limits`.
2. Переименовывает существующий slug `main` в `new-year`, сохраняя ID квиза, вопросы, участников и ответы. Если оба адреса уже заняты, останавливается без частичного обновления.
3. Заменяет публичные политики доступа и отзывает права `anon`/`authenticated` на таблицы приложения. Браузер больше не может читать эталонные ответы, изменять оценки или выдавать себя за другого участника через Supabase API.
4. Добавляет атомарную функцию `quiz_turn`, серверный таймер, блокировку изменения вопросов после начала игры и общий для серверных экземпляров лимит запросов.

Существующие вопросы, результаты и дополнительные столбцы сохраняются. Если в существующей `shown_questions` есть дубли пары участник/вопрос, создание уникального индекса остановит транзакцию: дубли нужно отдельно изучить, автоматически они не удаляются. Старые открытые вопросы с истёкшим сроком при продолжении будут записаны как пропуски.

Тест SQL в отдельной временной PostgreSQL, с ролями `anon`, `authenticated` и `service_role`:

```sh
psql "$TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase-schema.sql -f tests/database.sql
```

Используйте только одноразовую тестовую базу: схема меняет права доступа. Тестовые игровые данные откатываются через `ROLLBACK`.

## Маршруты

| Адрес | Экран |
| --- | --- |
| `/` | Каталог опубликованных квизов |
| `/quiz/:slug` | Начало или продолжение игры |
| `/quiz/:slug/results` | Результаты конкретного квиза |
| `/results` | Результаты с переключением между квизами |
| `/admin/quizzes` | Вход, создание квизов, редактор вопросов, публикация |
| `/admin/check` | Проверка ответов |
| `/select` | Совместимый переход в каталог |
| `/quiz/main` | Совместимый переход на `/quiz/new-year` |
| `/admin/questions` | Совместимый переход в редактор |

Новогодний квиз — обычная запись каталога; специальных экранов и новогоднего оформления нет.

## Vercel и Telegram

Перед публикацией согласуйте применение SQL, настройте серверные переменные в Vercel и проверьте приложение на тестовой базе. Сам деплой, настройка webhook и ротация ключей не выполняются автоматически.

`WEB_APP_URL` должен точно соответствовать origin открытого приложения: сервер отклоняет изменения с другого origin. Для preview-развёртывания нужен его собственный адрес в переменных окружения. В production cookie имеют флаги `Secure`, `HttpOnly`, `SameSite=Strict`.

Vercel обслуживает существующие серверные функции `/api/quiz` и `/api/bot`, SPA-fallback исключает `/api`, чтобы запросы к функциям не превращались в HTML. Остальные маршруты обслуживаются через fallback из `vercel.json`. Для бота используется HTTPS-адрес каталога. Кнопка в группе ведёт в личный чат с ботом, где доступна кнопка Mini App.

При регистрации webhook через Telegram Bot API укажите URL `WEB_APP_URL/api/bot` и параметр `secret_token`, равный `TELEGRAM_WEBHOOK_SECRET`. Не помещайте реальный токен в README, команды, историю терминала или логи. `GET /api/bot` — только проверка доступности HTTP-функции; он не проверяет настройки Telegram. `POST` без верного секретного заголовка отклоняется, а ошибки обработки возвращают 500 для повторной доставки Telegram.

В прежнем README был опубликован токен бота. Он удалён из документации, но его необходимо перевыпустить через BotFather и заменить в окружении и webhook. Простого удаления из файла недостаточно. Если проект ранее сохранялся в системе контроля версий, проверьте историю отдельно.

## Безопасность

Доступ к базе осуществляется только из `/api/quiz` через серверный ключ. Права администратора проверяются для каждого запроса; скрытие кнопок в UI не считается защитой. Администратор получает подписанную сессию на 8 часов, изменение пароля инвалидирует прежние сессии. При выходе очищается клиентский API-кеш.

Подпись Telegram проверяется по [официальной схеме HMAC](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), также проверяются срок `auth_date` (24 часа), тип и диапазон ID. Сервер получает ID участника из проверенной сессии; клиент не выбирает участника для сохранения ответа. Изменения проверяют точный `Origin`. Текст ограничен по длине и выводится средствами React без HTML-интерпретации.

Лимит входа — 10 попыток за 15 минут с одного IP; игровой API — 300 запросов в минуту с одного IP. Счётчики хранятся в PostgreSQL, IP заменён HMAC-отпечатком. За общим NAT лимит разделяется между участниками; для больших площадок его следует подобрать под нагрузку. Для массового публичного запуска дополнительно настройте ограничения запросов на стороне хостинга. Публичная таблица содержит только выбранное игровое имя, баллы и прогресс, без Telegram ID и username.

Модель доступа соответствует [рекомендациям Supabase по RLS и серверным ключам](https://supabase.com/docs/guides/database/postgres/row-level-security). До применения SQL прежние публичные политики в рабочей базе продолжают действовать.

## Проверка свободных ответов и Groq

Текущая версия намеренно сохраняет ручную проверку. Нормализация убирает различия регистра, `е`/`ё`, повторных пробелов и пунктуации. Перестановка одинаковых слов даёт подсказку организатору. Оценка остаётся ручной, поскольку порядок слов может менять смысл.

В примере «новогодняя игрушка на ёлку» и «ёлочные шары» ответ участника шире эталона. Для такой пары нужен критерий организатора: принимать ли общий класс предметов вместо конкретного предмета. Одного расстояния Левенштейна или совпадения слов недостаточно.

Возможное продолжение:

1. Хранить разрешённые организатором варианты ответа и применять точное нормализованное сравнение.
2. Использовать нечёткое совпадение только как подсказку об опечатке, не как окончательное решение.
3. Отправлять неоднозначные пары в модель через серверный адаптер Groq: вопрос, эталон, допустимые варианты и правило зачёта; без персональных данных участника. Ответ участника считать недоверенными данными, не инструкцией для модели.
4. Требовать структурированный результат `correct`, `incorrect` или `review`, краткое объяснение и сохранять версию модели. Добавить таймаут, кеш по паре ответов, бюджет и возврат к ручной проверке при ошибке или лимите.
5. Проверить качество на наборе размеченных организатором ответов до автоматического выставления баллов. Оставить ручное исправление решения и журнал изменений.

`GROQ_MODEL` — предполагаемое имя серверной переменной с ID модели, а не название бесплатной модели. Выбирать модель и лимиты нужно по [списку моделей Groq](https://console.groq.com/docs/models) и [ограничениям текущего аккаунта](https://console.groq.com/docs/rate-limits). Бесплатная доступность не гарантируется самим значением переменной. В этой версии Groq не вызывается, ключ не требуется и ответы третьим сторонам не отправляются.

## Проверки

```sh
npm run check
npm test
npm run format:check
npm run build
npm run test:ui
npm audit --omit=dev
npm audit
```

Браузерные тесты запускают установленный Google Chrome на desktop и экране 390×844. Если Chrome отсутствует, установите его или укажите подходящий Playwright channel в `playwright.config.ts`. Тесты используют перехват API с тестовыми данными, не рабочий Supabase. SQL проверяется отдельно на PostgreSQL. Проверка в настоящем Telegram и на рабочем Vercel остаётся отдельным шагом после согласованного обновления окружения и базы.

На момент проверки production-зависимости не содержат известных npm audit уязвимостей. В инструментах разработки остаётся предупреждение ReDoS для `picomatch` и использующих его Sass/Vite-пакетов; опубликованная последняя версия `picomatch` не содержит исправления. Автоматическое предложение audit понижает Vite до ранее уязвимой ветки, поэтому не применялось. Не используйте dev-сервер как публичный production-сервер; повторяйте аудит при обновлении зависимостей.

## Структура

```text
api/                    Vercel-функции приложения и Telegram-бота
server/                 Проверка подписи, сессии и валидация запросов
scripts/dev.mjs         Локальный запуск фронтенда и API на одном origin
src/app/                Redux store и типизированные RTK Query endpoints
src/components/         Навигационные и общие UI-компоненты, вход администратора
src/features/admin/     Управление квизами и ручная проверка
src/features/quiz/      Каталог и прохождение
src/features/results/   Результаты конкретного квиза
src/hooks/              Таймер и инициализация Telegram WebApp
src/lib/                Чистые функции сравнения ответов и форматирования
supabase-schema.sql     Проверяемая SQL-схема и обновление старой версии
tests/                  Проверки безопасности, API, SQL и браузерных сценариев
```
